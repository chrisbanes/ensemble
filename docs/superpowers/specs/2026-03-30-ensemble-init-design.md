# `ensemble init` — Interactive Setup Wizard

## Overview

`ensemble init` is an interactive CLI wizard that scaffolds a ready-to-run Ensemble configuration directory. It targets developers setting up Ensemble for their own repos, producing a zero-edit configuration that can immediately run `ensemble`.

Ensemble is an orchestration layer _above_ the repos it manages. The config directory is standalone — not inside any managed repo. A single Ensemble instance can orchestrate work across multiple repos, matching how issue trackers (GitHub Projects, Linear) span multiple repositories.

## Hard Dependencies

**acpx** is a hard dependency. Ensemble delegates all agent communication to acpx rather than managing agent processes directly. This eliminates per-agent executor logic, gives us session management and reconnection for free, and provides a uniform interface across Claude Code, Codex, Gemini, Copilot, and custom agents.

If acpx is not installed, `ensemble init` prints install instructions and exits.

## Directory Structure

The wizard creates:

```
my-orchestrator/
├── ensemble.yaml          # Generated by wizard
├── templates/             # Liquid prompt templates
│   ├── implement.liquid
│   └── review.liquid      # Only if multi-agent pipeline
└── TODO.md                # Only if todo_file tracker selected
```

No other files — no `.gitignore`, no README, no lock files.

## Wizard Flow

### Step 1 — Tracker

```
Where do your issues live?
  ❯ GitHub Projects
    TODO.md (great for trying things out)
```

### Step 2 — Tracker Credentials

**If GitHub:**
```
GitHub repository (owner/repo): acme/frontend
GitHub Project board number (optional, press enter to skip): 42
GitHub token ($GITHUB_TOKEN detected ✓)

Fetching board statuses...
  Found: Backlog, Todo, In Progress, Review, Done

Which statuses should Ensemble pick up work from? (space to toggle)
  [ ] Backlog
  [x] Todo
  [ ] In Progress
  [ ] Review
  [ ] Done

Which status means work is complete?
  ❯ Done

Which status means work failed?
  (enter a status name, or press enter to use "Failed"): Failed
```
Validates the token and repo/project accessibility inline. Pulls actual status field values from the board so the config matches what the user already has.

**If TODO.md:**
```
Creating TODO.md with a sample issue...
```
Pre-populates with a realistic example issue so there's something to run against immediately.

### Step 3 — Repos

```
Which repos should agents work in?

Add repo paths or URLs (enter blank line when done):
  1: /Users/chris/code/acme-frontend
     ✓ git repo
     Target branch for PRs [main]:
  2: /Users/chris/code/acme-api
     ✓ git repo
     Target branch for PRs [main]: develop
  3:
```

Validates each path is a git repo and that the target branch exists.

### Step 4 — Agent Discovery

acpx is used to discover and health-check available agents. Only healthy agents are shown.

```
Checking acpx... ✓ v0.8.0

Available agents:
  [x] claude      Claude Code v1.2.3
  [x] codex       Codex CLI v0.5.1
```

At least one agent is required to proceed. If no agents are discovered:

```
Checking acpx... ✓ v0.8.0

No agents found. Ensemble requires at least one coding agent.
Configure agents in acpx first, then re-run `ensemble init`.
See: https://github.com/openclaw/acpx
```

Agent discovery and custom agent configuration are acpx's responsibility. If a user wants to add a custom agent, they configure it in acpx first — then it appears in Ensemble's discovery list automatically.

### Step 5 — Agent Roles

Each selected agent gets a role name. The role is how the agent is referenced in the pipeline config — the underlying tool (claude, codex, etc.) is an implementation detail.

```
Name your agents by role:

  claude → role name [builder]: builder
  codex  → role name [reviewer]: reviewer
```

Defaults are `builder` for the first agent, `reviewer` for the second. If only one agent, defaults to `builder`.

### Step 6 — Pipeline

```
Pipeline steps define how agents process each issue.

Use default pipeline? (implement → review)
  ❯ Yes, use defaults
    No, let me customize
```

**Default pipeline:** `builder` implements, `reviewer` reviews. If only one agent, single `implement` step with no review.

**Custom pipeline:**
```
Step 1:
  Name: implement
  Agent: [builder ❯ reviewer]

Step 2:
  Name: review
  Agent: [builder ❯ reviewer]
  Depends on: [implement]

Add another step? (y/N): n
```

The wizard generates Liquid prompt templates in `templates/` for each step.

### Step 7 — Dry-Run Validation

After collecting all inputs, the wizard validates the entire configuration:

```
Validating configuration...

  ✓ acpx            v0.8.0 installed
  ✓ Tracker          GitHub Projects #42 on acme/frontend (3 active issues)
  ✓ Repo             /Users/chris/code/acme-frontend (git, branch: main)
  ✓ Repo             /Users/chris/code/acme-api (git, branch: develop)
  ✓ Agent: builder   claude, healthy via acpx (v1.2.3)
  ✓ Agent: reviewer  codex, healthy via acpx (v0.5.1)
  ✓ Pipeline         2 steps, no cycles
  ✓ Config schema    valid

All checks passed! ✓
```

**What each check does:**
- **acpx** — re-confirmed on PATH and responsive
- **Tracker** — for GitHub: authenticated API call to fetch issue count. For TODO.md: file exists and parses
- **Repos** — path exists, is a git repo, target branch exists
- **Agents** — spawn a quick acpx session per agent, confirm it responds, then cancel
- **Pipeline** — DAG validation via Kahn's algorithm (same logic as existing `EnsembleConfig`)
- **Config schema** — serialize the generated config and parse it back through `EnsembleConfig`

**On failure, the wizard offers inline fixes:**
```
  ✗ Repo   /Users/chris/code/acme-api — branch 'develop' not found

  Fix? (Y/n): y
  Target branch [main]: staging
  ✓ Repo   /Users/chris/code/acme-api (git, branch: staging)
```

If the user declines to fix, they can write the config anyway:
```
  1 check failed. Write config anyway? (y/N):
```

### Step 8 — Write Config

```
Writing configuration...
  ✓ ensemble.yaml
  ✓ templates/implement.liquid
  ✓ templates/review.liquid

Done! Run `ensemble` to start processing issues.
```

## Generated Config

Example output for GitHub + two repos + two agents:

```yaml
tracker:
  kind: github
  repository: acme/frontend
  api_key: $GITHUB_TOKEN
  project_number: 42
  active_states:
    - Todo
  terminal_states:
    - Done

repos:
  - path: /Users/chris/code/acme-frontend
    branch: main
  - path: /Users/chris/code/acme-api
    branch: develop

agents:
  builder:
    acpx_agent: claude
    prompt_template: templates/implement.liquid
  reviewer:
    acpx_agent: codex
    prompt_template: templates/review.liquid

steps:
  - name: implement
    agent: builder
    tracker_state: In Progress
  - name: review
    agent: reviewer
    depends:
      - implement
    tracker_state: Review

on_success: Done
on_failure: Failed
```

The `active_states` and `terminal_states` are populated from the actual board statuses selected during the wizard, not hardcoded defaults.

## Schema Changes to EnsembleConfig

This design requires the following additions to `ensemble-core`:

### New: `repos` field
`EnsembleConfig` gains `repos: Vec<RepoConfig>`:

```rust
pub struct RepoConfig {
    pub path: PathBuf,    // Local path or remote URL
    pub branch: String,   // Target branch for PRs
}
```

The workspace manager uses this to know what to clone/checkout per issue.

### New: `acpx_agent` field on AgentConfig
`AgentConfig` gains `acpx_agent: Option<String>` as the primary way to reference agents. When set, Ensemble invokes `acpx --agent <name>` instead of managing processes directly.

The existing `executor` field remains for backwards compatibility but `acpx_agent` takes precedence.

The `model` field becomes optional. When omitted, Ensemble does not pass a model flag to acpx — the agent uses its own default. The wizard does not ask about models; users can add this to the config manually if needed.

### Agent runtime simplification
With acpx as the communication layer, several `AgentRuntimeConfig` fields become acpx-level concerns rather than Ensemble's:
- `command` — replaced by `acpx_agent`
- `session_mode` — managed by acpx
- `permission_policy` — managed by acpx

### New CLI subcommand
`ensemble init` is added alongside the existing `ensemble [config]` run mode:

```
ensemble init    # Interactive setup wizard
ensemble [PATH]  # Run orchestrator (existing behavior)
```

## Edge Cases

| Scenario | Behavior |
|---|---|
| `acpx` not installed | Print install instructions, exit |
| No agents discovered | Print message to configure agents in acpx first, exit |
| GitHub token invalid | Inline retry during validation |
| Repo path doesn't exist | Inline retry during validation |
| Target branch doesn't exist | Inline retry during validation |
| `ensemble.yaml` already exists | "Config already exists. Overwrite? (y/N)" |
| User Ctrl+C mid-wizard | Nothing written, clean exit |
| Only one agent selected | Single-step pipeline (implement only), role defaults to `builder` |
| GitHub project has no Status field | Fall back to default states (Todo, In Progress, Done) |
