# Control Room Transcript Gap Closure Design

Date: 2026-04-15  
Status: Draft for review

## Goal

Close the remaining gaps between the shipped control-room transcript redesign and the original transcript design so the issue detail page satisfies the full frontend behavior described in the approved spec.

## Context

The current implementation already provides the core transcript shell:
- merged transcript rendering
- pinned composer and question banner
- supporting context tabs
- collapsed low-level activity
- transcript history windowing
- raw-event to transcript jump/highlight behavior

What remains is the part of the original design that was left implicit or only partially implemented:
- additional transcript entry families (`artifact_summary`, `warning`, `system_note`)
- transcript navigation controls (`Latest question`, `Current step`, `Latest activity`, and step-scoped expansion)
- sticky live-tail affordance when the user is reading older history
- explicit composer states for resolved/read-only and error/retry contexts
- graceful fallback messaging when one transcript source is missing or delayed

The user explicitly wants to try to complete all remaining spec gaps rather than stopping at a pragmatic subset.

## Requirements

1. Finish the remaining behaviors from `2026-04-14-control-room-transcript-design.md` without requiring immediate backend API changes.
2. Prefer frontend derivation of new transcript entry kinds when reliable source data already exists.
3. Keep transcript normalization separate from React rendering and page-shell control logic.
4. Preserve the current merged transcript UX, including history windowing and grouped low-level activity.
5. Add focused tests for the previously unimplemented controls, states, and fallback behavior.

## Product Model Additions

The run transcript remains the primary issue-detail surface, but its model and shell behavior expand in five areas.

### 1. Additional transcript entry families

The transcript normalization layer should support these new presentation-layer entry kinds:

- `warning`
- `system_note`
- `artifact_summary`

Derivation rules:
- `warning` should represent warning-like state transitions or risky-but-non-fatal conditions already visible in timeline data, such as retry scheduling or degraded-source states.
- `system_note` should represent shell-generated explanatory notes that help the operator interpret missing, delayed, or resumed data without pretending those notes came from the agent.
- `artifact_summary` should summarize available workspace or artifact context that is already surfaced elsewhere in the page and is useful in the transcript narrative.

These remain frontend transcript entry types, not new backend contract types.

#### Source-to-entry mapping

| Entry kind | Primary frontend source | Derivation rule | Fallback when source is absent |
| --- | --- | --- | --- |
| `warning` | timeline/live events | Normalize non-fatal risk states that are already represented by explicit event types or issue state, starting with retry scheduling and retry-active states | Omit the entry rather than inventing a warning |
| `system_note` | page/query state plus timeline/live availability | Normalize operator-facing explanatory notes generated by the shell, such as degraded source availability, transcript-source delays, or successful resume/reconnect notices | Omit unless the missing state would otherwise confuse the operator |
| `artifact_summary` | issue/workspace metadata already loaded by `IssueDetail` | Emit one concise summary entry when stable artifact/workspace context is available for the issue, starting with workspace path/context already shown in the shell | Omit the entry if no artifact/workspace metadata is available |

#### Precedence rule

- Use `warning` only for non-fatal problem states that correspond to real run or retry conditions.
- Use `system_note` for shell-generated explanatory context about data availability, resume/reconnect behavior, or transcript interpretation.
- If a state could fit both, prefer `warning` when it describes run risk, and `system_note` when it describes UI/data interpretation.

### 2. Transcript navigation controls

The transcript pane should gain a compact toolbar above the transcript list.

Controls:
- `Latest question` — jump to the newest unresolved `agent_question`
- `Current step` — jump to the newest transcript entry associated with the active workflow step
- `Latest activity` — return to the live tail of the transcript
- `Expand step activity` — expand grouped low-level activity related to the active step

These controls should operate on normalized transcript metadata rather than searching rendered DOM content.

Control semantics:
- If no unresolved `agent_question` exists, disable `Latest question`.
- If there is no active workflow step or no transcript entry associated with it, disable `Current step` and `Expand step activity`.
- `Current step` targets the newest normalized entry whose associated `stepName` matches the active workflow step.
- `Expand step activity` expands every grouped low-level activity entry currently present in the transcript whose member items are associated with the active workflow step.
- If a targeted entry or group lives inside hidden windowed history, auto-reveal enough history first, then highlight or expand it.

### 3. Sticky live-tail affordance

When the operator scrolls away from the bottom of the transcript and new entries arrive, the transcript should show a sticky `Scroll to latest` affordance.

Behavior:
- it appears only when the user is away from the tail and newer entries have arrived
- it returns the list to the newest visible activity
- it clears the pending unseen state once activated
- it should coexist with transcript history windowing and active-entry reveal behavior

### 4. Composer mode completion

The pinned composer should explicitly support four shell states:

1. `question` — pending interaction exists
2. `follow_up` — no pending interaction, but operator input is still allowed
3. `resolved` — the interaction is resolved or the run state makes the composer read-only
4. `error_retry` — the issue is in an error or retry-oriented state and the composer should frame recovery actions accordingly

The layout remains pinned and stable; the mode changes the banner/copy/available actions rather than swapping in unrelated page sections.

### 5. Fallback notes for partial data

The page should render the best partial transcript it can when conversation, interaction, or timeline data is unavailable or delayed.

Rules:
- do not block transcript rendering on any single source
- insert `system_note` entries only when the operator needs context to understand the gap
- keep raw errors and source-specific failures in the supporting context panel where appropriate
- if timeline history fails but live events are available, explain that degraded state inline and continue rendering the transcript from remaining sources

## Frontend Architecture

### Transcript normalization

`transcript-model.ts` should remain the source of truth for transcript entry derivation and ordering.

It should now additionally provide:
- derived entry kind selection for warnings, notes, and artifact summaries
- step association metadata used by transcript navigation and step-scoped expansion
- importance/navigation metadata so controls can target entries directly

Normalization still happens before rendering.

### Transcript shell state

`IssueDetail.tsx` should own shell-level transcript state:
- active transcript entry id
- live-tail/unseen activity state
- current-step jump target
- latest-question jump target
- step-expansion requests

`RunTranscript.tsx` should own rendering-time behaviors tied to scrolling and visibility:
- visible tail windowing
- auto-reveal for hidden active entries
- scroll tracking
- sticky `Scroll to latest` control
- per-entry rendering based on parent-provided control state

### Entry rendering

`TranscriptEntryRenderer` should dispatch the new entry families to focused components:
- `WarningEntry`
- `SystemNoteEntry`
- `ArtifactSummaryEntry`

Existing entry renderers remain responsible only for presentation, not derivation.

### Composer

`IssueComposer.tsx` should accept an explicit mode or sufficient shell props to derive one consistently. The component should stop implying that every non-question state is simply a generic follow-up state.

## Data Flow

1. `IssueDetail` fetches issue detail, conversation, interaction, persisted timeline events, and live websocket events.
2. The transcript model merges those inputs into a richer transcript entry stream.
3. The page computes navigation targets and fallback notes from normalized entries and page state.
4. `RunTranscript` renders the current visible tail and exposes the scroll-to-latest behavior.
5. Toolbar controls target known entry ids or step-scoped activity groups.
6. The composer reflects the current shell mode while the context panel continues exposing workflow, logs, artifacts, and raw events.

## Error Handling

- If a navigation control has no valid target, disable it rather than failing silently.
- If an active entry is hidden by transcript windowing, auto-expand the visible window just enough to mount it.
- If timeline history is unavailable, continue rendering from conversation, interaction, and live events, with an inline `system_note` that explains the degraded state.
- If artifact context is unavailable, omit `artifact_summary` entries rather than rendering placeholders.
- If the issue is complete or otherwise not interactive, show a stable resolved/read-only composer state instead of a dead input.

## Testing Strategy

Add or extend frontend tests for:

1. transcript derivation of `warning`, `system_note`, and `artifact_summary`
2. toolbar jump behavior for latest question, current step, and latest activity
3. step-scoped expansion of grouped low-level activity
4. sticky live-tail affordance when new entries arrive while reading older history
5. composer mode switching across question, follow-up, resolved, and error/retry states
6. degraded-source fallback behavior when conversation, interaction, or timeline data is missing or delayed

## Recommendation

Implement the remaining gaps as a frontend-first extension of the shipped transcript shell.

That keeps the current architecture intact, satisfies the original product intent, and avoids a backend-model detour unless implementation proves a specific entry family cannot be derived reliably from existing data.
