## Delivered behavior

Overview, project and cross-project List/Board, Inbox pending requests, recovery
links and ordinary legacy assignment links open `/app/tasks/:id`. The workspace
retains exact source/result/assignment/request anchors, literal bounded history,
pending requests outside disclosures, captured context, scoped supplied evidence,
read-only delivery observations and separate local/GitHub reply lifecycles.
Search opens exact retained task/decision/result records and restores dates,
filters, selected-match focus, scroll and the original workspace. Board return
also restores column, horizontal reading position and task-link focus.

Imported requirements stay source-owned; state-only imported configuration does
not manufacture a local source revision. Search filters by current task project
while retaining captured provenance after actual `github.place` transfer.
Criterion extraction covers supported literal checklists only. With no structured
records, the UI directs the operator to the supplied brief; it does not claim no
criteria were supplied. Captured references do not establish that an agent read them.

Result metadata and receipts are atomic and immutable; compound feedback anchors
must bind the exact result's retained relationships. Artifact preview is limited
to recorded regular PNG/JPEG files in the task's current canonical workspace,
with bounded handle reads, MIME/identity checks, alias re-resolution and access/
redaction/revision revalidation after awaits. It accepts no client path or proxy fetch.

Local feedback retains an editable exact-anchor draft. The accountable lead must
actually be pending/running. Completed or held leads reject without dispatch or
reopening and explain the unavailable destination. Successful browser feedback
uses a real delegated result with a genuinely pending lead, rather than SQL reopening.
GitHub posting uses a server-constructed issue-comment-only actor, existing grants,
holds and serialization, and a distinct durable exact-material review/confirm
binding in approval mode. Unknown local/remote replies keep the original key and
body through unrelated viewing/provider-refresh commands and reconcile without
duplicate sends.
